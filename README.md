# Stockhold

Stockhold — сервис резервирования товарных остатков при оформлении заказа. Он позволяет другому сервису ненадолго зарезервировать товар, предотвращает продажу одного и того же остатка нескольким покупателям и публикует изменения остатков для других систем.

Основной интерфейс — **gRPC с версионированным контрактом Protocol Buffers**. Состояние остатков хранится в PostgreSQL. Транзакционный outbox записывает события в той же транзакции, в которой меняется остаток; отдельный обработчик отправляет их в Kafka-совместимый брокер. Для локальной разработки в проект включена Redpanda.

```text
сервис оформления заказа ──gRPC──► Stockhold ──транзакция──► PostgreSQL
                                                           ├─ items / reservations
                                                           └─ outbox_events
                                                                 │ отправка
                                                                 ▼
                                                            топик Kafka
                                                                 │
                                                                 ▼
                                                     аналитика / выполнение заказов
```

## Зачем нужны эти компоненты

- **gRPC/Protobuf:** явный генерируемый контракт для вызовов между сервисами; клиенты получают типизированные коды статуса и сообщения.
- **PostgreSQL:** условные обновления и блокировки строк сохраняют корректность остатков при одновременных запросах.
- **Транзакционный outbox:** каждой зафиксированной брони соответствует зафиксированное событие для публикации. Недоступность Kafka не откатывает операцию оформления заказа.
- **Kafka-совместимые события:** другие системы узнают о бронировании, подтверждении, отмене, истечении срока и пополнении без постоянного опроса базы остатков.

Сервис намеренно ограничен по составу: Go, PostgreSQL, gRPC, один клиент Kafka и Docker Compose. Здесь нет фреймворка, кэша, обработки платежей или платформы оркестрации.

## Локальный запуск

Потребуется Docker Compose. Скопируйте `.env.example` в `.env`, задайте собственный секретный `API_KEY` и выполните:

```sh
docker compose up --build -d
```

В PowerShell файл можно скопировать командой `Copy-Item .env.example .env`. gRPC-сервер слушает `127.0.0.1:9090`, внешний Kafka-адрес Redpanda — `127.0.0.1:19092`. PostgreSQL доступен только внутри сети Compose. Учётные данные базы данных, заданные в `compose.yaml`, предназначены для локальной разработки.

Встроенный CLI позволяет быстро проверить gRPC API. Запускайте его внутри контейнера приложения: ключ он берёт из `.env`.

```sh
docker compose exec api /stockholdctl health
docker compose exec api /stockholdctl create-item CAM-01 "Compact camera" 10
docker compose exec api /stockholdctl reserve CAM-01 2 300 checkout-2026-0001
docker compose exec api /stockholdctl get-item CAM-01
```

Возьмите `reservation.id` из ответа на `reserve` и выполните `docker compose exec api /stockholdctl confirm <id>`. Для локального окружения, доступного только через loopback-интерфейс, CLI использует gRPC без TLS. Чтобы запускать клиент на хосте, установите Go 1.25+, задайте `API_KEY` в командной оболочке и используйте `go run ./cmd/stockholdctl <command>`. При подключении к развёрнутому сервису с TLS укажите `-tls` и при необходимости `-ca cert.pem`.

Чтобы посмотреть поток событий в локальном брокере:

```sh
docker compose exec redpanda rpk topic consume stockhold.events.v1 -n 4 -X brokers=redpanda:9092
```

Сервер также можно запустить напрямую с Go 1.25+ и PostgreSQL 16+. Задайте `DATABASE_URL`, `API_KEY` и, если нужно, `KAFKA_BROKERS`, затем выполните `go run ./cmd/stockhold`. Если брокер не настроен, зафиксированные события остаются в outbox и могут быть отправлены после его настройки.

## Контракт gRPC

Исходный контракт находится в [`api/stockhold/v1/stockhold.proto`](api/stockhold/v1/stockhold.proto). Сгенерированный Go-код клиента и сервера включён в репозиторий в каталоге `gen/stockhold/v1`, поэтому для сборки и запуска сервиса `protoc` не требуется.

| RPC | Назначение |
| --- | --- |
| `CreateItem` / `GetItem` | Создать SKU и получить физический и доступный остаток. |
| `Restock` | Пополнить остаток с защитой ключом идемпотентности. |
| `Reserve` | Зарезервировать количество товара на 1–900 секунд с защитой ключом идемпотентности. |
| `GetReservation` | Получить текущее состояние брони, при необходимости применив истечение срока. |
| `Confirm` / `Cancel` | Завершить ожидающую бронь. |

Для вызовов нужен gRPC-метаданный параметр `x-api-key`. Стандартный вызов проверки состояния gRPC `Check` доступен без ключа и проверяет готовность PostgreSQL. Ошибки возвращаются с кодами gRPC, например `InvalidArgument`, `NotFound`, `AlreadyExists`, `FailedPrecondition` и `Aborted`.

Чтобы заново сгенерировать код после изменения контракта, установите `protoc`, `protoc-gen-go` и `protoc-gen-go-grpc`, затем выполните из корня репозитория:

```sh
protoc -I . --go_out=. --go_opt=module=stockhold \
  --go-grpc_out=. --go-grpc_opt=module=stockhold \
  api/stockhold/v1/stockhold.proto
```

## Гарантии для остатков и событий

`on_hand` — физический остаток, который ещё не продан. `available` — `on_hand` за вычетом активных броней. Ограничения PostgreSQL поддерживают `0 <= available <= on_hand`. Операция `Reserve` условно уменьшает `available`; `Confirm` уменьшает `on_hand`; `Cancel` и истечение срока восстанавливают `available`; `Restock` увеличивает оба значения.

Outbox и состояние остатков фиксируются вместе. Каждое событие получает возрастающий `aggregate_sequence` для своего SKU. Обработчик отправляет следующее событие для SKU только после подтверждения предыдущего; события разных SKU могут обрабатываться независимо. Для публикации используется аренда записи; неудачные отправки повторяются с увеличивающейся задержкой. Публикация в Kafka имеет гарантию **как минимум однократной доставки**: если Kafka примет событие, но процесс завершится до записи подтверждения в PostgreSQL, то же событие может быть отправлено повторно. Потребители должны удалять дубликаты по `event_id`. Ключом сообщения служит SKU, чтобы события одного товара попадали в одну партицию, пока количество партиций и алгоритм распределения ключей остаются прежними.

События публикуются в `stockhold.events.v1` как версионированный JSON (`schema_version: 1`). Типы событий: `stock.item_created`, `stock.restocked`, `reservation.created`, `reservation.confirmed`, `reservation.cancelled` и `reservation.expired`. Пример сообщения и точное описание транзакций приведены в [документе об архитектуре](docs/architecture.ru.md).

Проверка состояния gRPC подтверждает доступность базы данных, но не брокера. Если Kafka недоступна, API продолжает резервировать товар, а число ожидающих событий в outbox растёт. В рабочем окружении отслеживайте результат запроса `SELECT count(*) FROM outbox_events WHERE published_at IS NULL`.

## Настройка

| Переменная | Обязательна | По умолчанию | Назначение |
| --- | --- | --- | --- |
| `DATABASE_URL` | Да | — | URL подключения к PostgreSQL. |
| `API_KEY` | Да | — | Общий ключ API длиной не менее 16 символов. |
| `GRPC_LISTEN_ADDR` | Нет | `127.0.0.1:9090` | Адрес, который слушает gRPC-сервер. |
| `KAFKA_BROKERS` | Нет | — | Адреса брокеров через запятую; пустое значение отключает отправку событий. |
| `SWEEP_INTERVAL` | Нет | `2s` | Интервал проверки истёкших броней: от `1s` до `1h`. |
| `OUTBOX_INTERVAL` | Нет | `1s` | Интервал проверки outbox: от `1s` до `1h`. |
| `TLS_CERT_FILE`, `TLS_KEY_FILE` | Нет | — | Укажите оба значения для запуска gRPC через TLS. |

## Тесты и ограничения

```sh
go test ./...
go vet ./...
```

Для запуска интеграционных тестов задайте `TEST_DATABASE_URL`, указывающий на **одноразовую** базу PostgreSQL с именем, оканчивающимся на `_test`. Перед каждым сценарием тесты очищают таблицы приложения. В CI тесты с PostgreSQL запускаются с детектором гонок Go; также собирается образ контейнера.

Тесты охватывают одновременные запросы на бронирование, повторы с одним ключом, переходы между состояниями, истечение срока во время заблокированного подтверждения, контракт gRPC, создание событий в outbox, повторную отправку после ошибки публикации и восстановление аренды. При работающем брокере задайте `TEST_KAFKA_BROKERS=127.0.0.1:19092` и выполните `go test -run '^TestKafkaDelivery$' ./internal/stockhold`, чтобы проверить доставку события из outbox в топик. В CI этот тест с Redpanda запускается после набора тестов с PostgreSQL.

Stockhold не обрабатывает платежи и не синхронизирует данные с внешним складом. Завершённые брони и ключи идемпотентности хранятся до добавления явной политики хранения и удаления. Для эксплуатации нужны отдельные учётные данные, TLS, ротация ключей, резервные копии, оповещения о накоплении событий в outbox, а также заранее созданный топик Kafka с подходящими настройками партиций и срока хранения.
