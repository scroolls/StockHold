# Архитектура Stockhold

Stockhold выдаёт кратковременные резервы товара для другого сервиса, например checkout. Он не знает покупателей и платежи. Внешний сервис хранит связь своего заказа с `reservation.id`, после успешной оплаты вызывает `Confirm`, а при отказе — `Cancel`.

## Состав системы

```text
checkout / warehouse
        │ gRPC, protobuf, x-api-key
        ▼
  Stockhold Service
    ├─ проверка входных данных и статусы gRPC
    ├─ операции хранения ── транзакция ──► PostgreSQL
    │                                      ├─ items
    │                                      ├─ reservations
    │                                      ├─ stock_receipts
    │                                      └─ outbox_events
    ├─ обработчик просроченных броней ────► PostgreSQL
    └─ outbox dispatcher ─────────────────► Kafka topic
                                             │
                                             └─ downstream consumers
```

- `api/stockhold/v1/stockhold.proto` — версия внешнего контракта. В `gen/stockhold/v1` хранится сгенерированный код сервера и клиента.
- `internal/grpcapi` — реализация RPC, проверка ключа, коды ошибок, gRPC health. SQL и правила остатков здесь не размещены.
- `internal/stockhold` — операции над данными, блокировки, миграции и транзакционный outbox.
- `internal/outbox` — фоновая отправка событий и адаптер Kafka. Сбой Kafka не влияет на уже зафиксированную бронь.
- `cmd/stockhold` — настройка, запуск, таймеры и остановка сервера. `cmd/stockholdctl` — минимальный gRPC-клиент для проверки и демонстрации контракта.

## Модель остатков

Таблица `items` содержит SKU, название, `on_hand` и `available`. `on_hand` — ещё не проданное физическое количество. `available` — количество без активных броней. Ограничения PostgreSQL поддерживают `0 <= available <= on_hand`.

| Операция | `on_hand` | `available` |
| --- | ---: | ---: |
| Новая бронь на `q` | без изменения | `-q` |
| Подтверждение | `-q` | без изменения |
| Отмена или истечение срока | без изменения | `+q` |
| Пополнение | `+q` | `+q` |

Пусть товар создан с 10 единицами. После брони 3 единиц значения будут `10/7`. Подтверждение даёт `7/7`; отмена вместо подтверждения вернула бы `10/10`.

Таблица `reservations` хранит ключ идемпотентности, хеш параметров, срок и статус. Статусы: `pending`, `confirmed`, `cancelled`, `expired`. `stock_receipts` хранит ключи выполненных пополнений. Название таблицы — историческое: каждая запись обозначает успешно принятый запрос на пополнение.

## Конкурентное бронирование

`Reserve` открывает транзакцию, вставляет строку брони с уникальным `idempotency_key`, затем выполняет:

```sql
UPDATE items
SET available = available - $2
WHERE sku = $1 AND available >= $2;
```

Успех требует изменения ровно одной строки. PostgreSQL блокирует обновляемый товар. Если два запроса пытаются взять последние единицы, второй видит актуальный остаток после завершения первого. При нехватке транзакция откатывается целиком, включая новую бронь и ключ идемпотентности. После пополнения тот же запрос можно повторить.

Уникальный ключ вставляется до изменения товара. Одновременный повтор идентичного запроса ждёт исходную транзакцию и читает её результат. Если ключ совпал, а параметры отличаются, возвращается `Aborted`; остаток не меняется. Ключи пополнений и броней хранятся в отдельных таблицах и не смешиваются.

## Завершение и истечение срока

`Confirm` и `Cancel` сначала блокируют строку брони с `FOR UPDATE`. Подтверждение проверяет дедлайн после получения блокировки, поэтому запрос, пришедший до дедлайна, но ожидавший другую транзакцию, не подтвердит уже просроченную бронь. Повтор того же действия не меняет остаток второй раз. Несовместимый переход отклоняется.

Фоновая обработка выбирает до 100 просроченных `pending`-строк через `FOR UPDATE SKIP LOCKED`. Несколько процессов могут брать разные брони без дублирования работы. Изменение статуса, возврат товара и создание события выполняются в одной транзакции. Если процесс останавливается, строки остаются в PostgreSQL и обрабатываются после перезапуска. Чтение конкретной просроченной брони также приводит её к `expired`.

## Транзакционный outbox

Прямая последовательность «записать бронь в БД, затем отправить событие в Kafka» теряет событие, если процесс завершится между этими действиями. Поэтому запись в `outbox_events` добавляется **в ту же PostgreSQL-транзакцию**, что и изменение остатка. Состояние и событие фиксируются вместе либо вместе откатываются.

Создаются события `stock.item_created`, `stock.restocked`, `reservation.created`, `reservation.confirmed`, `reservation.cancelled` и `reservation.expired`. Повтор запроса с тем же ключом не создаёт новое событие. Сообщение содержит постоянный `event_id`, `schema_version`, порядковый номер события для товара, тип, SKU, количество, время и, для брони, её идентификатор и статус. Например:

```json
{
  "schema_version": 1,
  "event_id": "4d4922c1-04a3-4e19-b48e-187fa94394f3",
  "aggregate_sequence": 2,
  "type": "reservation.confirmed",
  "reservation_id": "70ba4dcc-32f3-4300-8f1e-06ec18d950ce",
  "sku": "CAM-01",
  "quantity": 2,
  "status": "confirmed",
  "occurred_at": "2026-10-17T12:00:00Z"
}
```

Payload — JSON версии 1, topic — `stockhold.events.v1`. Каждое изменение товара увеличивает `items.event_seq` в той же транзакции. Dispatcher не берёт следующее событие SKU, пока предыдущее не отмечено опубликованным. Kafka key равен SKU: события одного товара попадают в один раздел при неизменном числе разделов и использовании хеш-балансировщика. При повторной доставке потребитель должен проверять `event_id` и при необходимости `aggregate_sequence`.

## Публикация и сбои

Dispatcher выбирает одно готовое событие за раз. Одним SQL-запросом он ставит 30-секундную аренду и токен владения. После этого вне транзакции отправляет сообщение в Kafka, ожидая подтверждения брокера. На успешную отправку даётся до 10 секунд. После подтверждения dispatcher помечает строку как опубликованную, сверяя токен аренды.

При ошибке строка снова становится доступной после задержки. Интервал увеличивается от одной секунды до минуты. Если процесс завершился после захвата строки, аренда истечёт и другой экземпляр повторит публикацию. `FOR UPDATE SKIP LOCKED` позволяет нескольким dispatcher-процессам выбирать разные строки. Для одного SKU публикация идёт последовательно; разные товары могут обрабатываться параллельно.

Гарантия доставки — **at least once**. Брокер может принять сообщение, а процесс может завершиться до фиксации `published_at`. В этом случае будет повторная публикация с тем же `event_id`. Потребитель обязан сохранять обработанные `event_id` и пропускать дубликаты. Гарантия exactly once не заявляется.

Недоступность Kafka не откатывает уже принятую бронь. События накапливаются в базе и отправляются после восстановления брокера. gRPC health проверяет PostgreSQL; отставание outbox нужно наблюдать отдельно, например запросом `SELECT count(*) FROM outbox_events WHERE published_at IS NULL`. При длительном отказе брокера рост таблицы требует оперативного внимания.

## Контракт, безопасность и ошибки

Основной интерфейс определён в `.proto`: `CreateItem`, `GetItem`, `Restock`, `Reserve`, `GetReservation`, `Confirm`, `Cancel`. Количество и срок проверяются до SQL. Сервер отклоняет сообщения крупнее 64 КиБ и использует стандартные коды gRPC: `InvalidArgument`, `NotFound`, `AlreadyExists`, `FailedPrecondition`, `Aborted`, `Internal`.

Для прикладных RPC требуются метаданные `x-api-key`. Хеш ключа сравнивается за постоянное время; значение не пишется в журналы. Стандартный gRPC health `Check` открыт для проверки готовности. В локальном Compose gRPC доступен только на loopback хоста. Для внешнего развёртывания поддерживаются `TLS_CERT_FILE` и `TLS_KEY_FILE`; CLI умеет проверять TLS и пользовательский CA. При одном общем ключе нет разграничения клиентов: для многопользовательской эксплуатации нужны отдельные учётные данные и ротация.

Логи — структурированный JSON: метод, код ответа, длительность, ошибка публикации и идентификатор события. Полные тела запросов и секреты не журналируются.

## Запуск и проверка

`compose.yaml` запускает PostgreSQL 16, Redpanda с Kafka-совместимым API и сервис. Образ приложения содержит сервер и консольный gRPC-клиент. Контейнер использует непривилегированного пользователя. При старте сервер применяет три миграции под advisory lock и продолжает отправку ранее накопленных событий.

Интеграционные тесты используют отдельную базу с суффиксом `_test`; они очищают таблицы перед каждым сценарием. Проверяются гонки за остаток, повтор ключа, переходы состояний, истечение срока во время блокировки, gRPC-вызовы, создание событий, ошибка отправки, повтор и восстановление аренды. Заменяемый Publisher позволяет детерминированно проверить dispatcher без внешнего брокера. Отдельный тест с `TEST_KAFKA_BROKERS` проверяет доставку outbox-события в Kafka-совместимый брокер; CI запускает его с Redpanda. Локальные команды находятся в `README.md`.

## Текущие границы

Сервис не проводит платежи, не синхронизирует внешний склад и не хранит историю клиентов. Брони и ключи идемпотентности сохраняются бессрочно, пока не задана политика очистки. Для промышленной эксплуатации дополнительно нужны мониторинг отставания outbox, резервное копирование базы, управление секретами, предварительно созданный Kafka topic, настройка разделов и хранения сообщений, а также согласованные версии событий для потребителей.
